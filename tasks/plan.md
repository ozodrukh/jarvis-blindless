# Implementation plan: configurable Jarvis voice

User approved the capability map and explicitly requested implementation on 2026-10-24. This authorizes proceeding through specs, planning, and implementation without another intermediate approval. Specs are the four root SPEC files indexed by CAPABILITY-MAP.md.

Keep Swift/Python and macOS 14. Use installed Whisper/Gemma/macOS speech, standard-library HTTP, no agent framework or new model downloads. JSON config is owned by Python; Swift remembers the selected file and validates it through the worker's lightweight validation mode. Network stages run outside audio ingestion and are cancellable. Decisions and actual player effects remain separate.

Order and checkpoints are in todo.md: configuration → online routing → capture/control → worker integration → native UI/playback → package verification. Audio regression tests can be written independently against the agreed Capture/end-chat interface. Shared production files are edited sequentially. No Git repository is present; preserve a local source baseline in .build/before-online-routing instead of inventing history.

Risks: audio/LLM coupling requires explicit supported combinations; cancellation must not let old results act; tiny Whisper quality is unmeasured for full requests; streaming audio timing differs from hardware; remote voice/model availability is user-specific. Mitigations: direct-audio route preservation, cancellation tests, recorded-speech smoke checks, stage metrics, and an honest hardware checklist. Real service credentials and a live user voice are unavailable, so mocked HTTP and recorded local speech verify those boundaries while live checks remain stated limits.

## Активный план: восстановление системного микрофона

**Статус:** план и задачи утверждены пользователем 2026-10-24; пользователь явно поручил реализацию. MIC-1–3 реализованы, полный набор тестов, release-сборка и проверка подписи пройдены; первый живой запуск подтверждён пользователем — обе шкалы работают; полные циклы аппаратной части MIC-4 остаются открытыми. Спецификация: утверждённое дополнение «Восстановление системного микрофона» в `SPEC-audio-input.md`, модуль `audio-input`. Согласование относится к этому исправлению; код захвата обновлён. Задачи и контрольные точки находятся в `tasks/todo.md`, раздел `MIC`.

### Результат

Jarvis корректно освобождает аудиозахват и восстанавливает его после смены маршрута, не оставляя системный микрофон без сигнала. Проверяются оба режима обработки голоса. Диагноз о повторном использовании повреждённого состояния движка остаётся гипотезой до аппаратного сравнения.

### Решения и порядок реализации

1. **MIC-1 — запуск и остановка с полным освобождением.** Сделать движок ресурсом отдельного сеанса захвата вместо постоянно живущего поля `VoiceBridge`. Один сеанс владеет движком, tap и наблюдателем конфигурации; очистка работает при частичной инициализации, повторной остановке и ошибке. При новом запуске создавать новый движок. Ошибки включения обработки голоса обрабатывать явно; обычный резервный захват поднимать на свежем сеансе после очистки неудачного. Сначала добавить регрессионные XCTest с управляемыми отказами через минимальную точку подмены операций захвата; не создавать общий аудиофреймворк.
2. **MIC-2 — безопасное восстановление маршрута.** Отделить желание пользователя слушать от факта работающего движка. Сериализовать переходы состояния на главной очереди; идентификатор сеанса защищает callbacks из аудиопотока. Инвалидировать сеанс до остановки. Поздние разрешения микрофона, события старого движка, PCM и отложенные работы проверяют актуальность. На событие смены конфигурации освободить прежний сеанс, сгруппировать повторные события и заново прочитать формат. Предлагаемый предел — максимум три попытки в общем окне пяти секунд после последнего изменения маршрута; новая ручная команда запуска начинает новую попытку. При исчерпании — освобождение ресурсов и ошибка. Сохранить постановку книги на паузу при смене устройства.
3. **Контрольная точка A.** Целевые тесты и сборка проходят. Проверить поведение выключения во время восстановления и после запроса разрешения. Просмотреть изменения относительно требований; не расширять работу на Python, модели и плеер без необходимости.
4. **MIC-3 — готовность и диагностика реального захвата.** Различать отсутствие callbacks и тихие буферы. Учитывать время первого/последнего буфера и число буферов в границах сеанса. Сообщать готовность только после успешного старта и получения первого пригодного буфера; ограничить ожидание первым окном в пять секунд, затем очистить захват с ошибкой. Отсутствие буферов у уже работающего захвата также обрабатывать ограниченно в рамках политики MIC-2; тишина этого не вызывает. Исключить использование старого индикатора после остановки. Журналировать только события переходов, фактический режим, формат и сводные счётчики/времена, без PCM, текста речи и настроек провайдеров.
5. **MIC-4 — сборка и аппаратное сравнение.** Запустить полный набор тестов, собрать и проверить подпись приложения. Проверить оба режима и все циклы из спецификации на Mac пользователя: два одновременных индикатора, другое приложение с уже разрешённым входом, 10 переключений микрофона, 5 перезапусков голоса, 5 изменений маршрута и 5 полных перезапусков приложения. Сначала зафиксировать исходный сбой, затем сравнить исправление; при невозможности воспроизведения указать это явно. Проверять с установленным Background Music, не отключая/удаляя драйвер. Если существующий интерфейс позволяет временно менять его активный маршрут в рамках проверки, записать фактические условия, не назначая виртуальный вход поддерживаемым сценарием. Записать результаты и непроверенные пункты в `docs/verification.md`. Архив обновлять только после определения результата аппаратной проверки; непроверенную сборку не объявлять исправленным выпуском.

### Зависимости и проверка

`MIC-1 → MIC-2 → контрольная точка A → MIC-3 → MIC-4`.

Правки общего состояния выполняются последовательно. Новые агенты для этого плана не требуются. Документирование аппаратных условий возможно независимо от кода, но вывод об исправлении зависит от MIC-1–3. Для каждой задачи предусмотрен регрессионный тест, когда проверяется программная логика; аппаратные проверки не заменяются mock-тестами. Полные исполняемые команды находятся в утверждённой спецификации, целевые команды также записаны в списке задач.

### Риски и ограничения

| Риск | Последствие | Проверка/мера |
|---|---|---|
| Пересоздание движка не устраняет сбой macOS | Системная шкала остаётся без сигнала | Раннее сравнение старого и нового жизненного цикла; продолжить локализацию, не объявлять гипотезу доказанной. |
| Смена маршрута генерирует новые события при запуске | Цикл перезапусков | Проверка владельца события, группировка уведомлений, ограничение числа попыток и времени. |
| Поздний callback или ответ на разрешение | Возобновление выключенного захвата | Отдельное намерение слушать и проверка идентификатора сеанса на границах очередей. |
| Новый движок удерживается замыканием | Системные ресурсы не освобождаются | Избегать циклов владения, удалять наблюдатель/tap, проверять освобождение тестовой реализации. |
| Первый callback запаздывает | Ложная готовность или ложный отказ | Отдельное состояние запуска, измерение времени, аппаратная проверка обоих режимов. |
| Нет доступа к нативному интерфейсу проверки | Нельзя подтвердить системную шкалу | Подготовить сборку и точный сценарий; отметить физическую проверку как незавершённую и запросить результат пользователя. |

Нельзя менять системный вход, громкость, mute или разрешения автоматически, перезапускать `coreaudiod` либо менять личный JSON. Настройки моделей и оплачиваемые запросы не нужны для проверки жизненного цикла.

### Согласование

Технический план и связанные задачи утверждены пользователем вместе; получено явное поручение перейти к разработке. Следующий незавершённый шаг — аппаратная проверка MIC-4. Неподтверждённые технические вопросы из спецификации закрываются измерениями, а не дополнительными предположениями.


## TTS: настраиваемый формат озвучки

Согласовано пользователем 2026-10-24 с явным поручением реализовать. Основание: дополнение в SPEC-model-routing.md. Предыдущие задачи, включая аппаратные проверки микрофона, сохраняются. Нового промежуточного согласования не требуется.

Порядок: TTS-1 (конфигурация и raw PCM) → TTS-2 (контейнеры и ограниченное декодирование) → контрольная точка тестов → TTS-3 (проверка нативного плеера настоящими образцами) → TTS-4 (документация, текущий Gemini-конфиг и штатная сборка). Работать последовательно; HTTP/декодирование выполняются в существующем прерываемом потоке запроса, чтобы сохранять сетевой бюджет и отмену. Ogg/Opus декодируется уже установленной soundfile. Остальные контейнеры проверяются и передаются нативному плееру; если испытание выявит несовместимость, использовать существующие декодеры и уточнить запись в спецификации. Новых зависимостей нет.

Риски: параметры PCM из HTTP могут отличаться от настроек; раздувание сжатого аудио требует ограничения до декодирования; сырые байты без контейнера нельзя давать AVAudioPlayer; AAC/Opus требуют реальных образцов. Меры: строгие заголовки и тесты границ, ограниченный выход WAV, подготовка AVAudioPlayer и чтение ненулевого сигнала, live-запрос к выбранной Gemini. На этом Mac нет гарантии проверки минимальной macOS 14 — фактическая ОС и оставшиеся аппаратные ограничения будут записаны в docs/verification.md.

Git-репозитория нет; исходное состояние файлов сохранено в .build/before-tts-formats. Перечень задач и проверок — tasks/todo.md.

TTS завершено: все 66 Python-тестов в штатной среде и 32 Swift-теста прошли; release-сборка и подпись проверены; live Gemini вернула корректный WAV за 1,637 с без резерва. Проверка системного воспроизведения с нулевой громкостью прошла. Ограничения macOS 14 и ручного прослушивания записаны в docs/verification.md. Старые аппаратные задачи MIC остаются открытыми.
